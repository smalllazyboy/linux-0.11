### proc文件系统的实现
#### 问题
Q：“计算机上有哪些文件” 这个信息 应该会有一个存储的地方，那么是在哪里存储的？
A：[分区起始] → 引导块 → 超级块 → 组描述符表 → inode位图 → inode表 → 数据块位图 → 数据块 → [下一个块组](不同操作系统的文件系统不同，这是类 Unix 文件系统)。超级块当中存放着现有的根目录的磁盘号，对应的磁盘中就存储了该根目录下的内容，若是一个目录a，则会存放索引号，通过该索引就可以在组描述符表中找到目录a对应的磁盘号等相关信息。而目前所要实现的proc文件系统并没有真实地存放在磁盘（也是硬盘）上，所以是一个虚拟的文件系统。

Q：proc虚拟文件夹会被显示，所以文件夹的显示原理是什么？
A：根据实验提示，系统初始化会负责挂载根文件系统，似乎就是这个操作成功识别了硬盘上的文件系统（或许挂载就是这个意思）。而proc文件夹的显示是通过mkdir实现，结点（或许就是文件吧）则通过mknod实现。通过这些操作之后就能在对应的目录上创建相应的内容并显示，所以这些步骤会在操作硬盘，在硬盘上存储这些相关信息，显示的话就是另一个模块（视觉模块又或者是命令行（例如ls）模块）的功能了。

Q：竟然文件夹的创建是通过mkdir实现，那么应该是存储在了磁盘上才对吧？
A：该方式应该是这个实验的模拟方法，正式的linux系统实现了虚拟文件系统，且实现了增加新文件系统的接口。所以如果通过提示的方式实现proc文件系统，该文件夹应该是会存储在硬盘上的。

Q：什么是文件系统？似乎有很多文件系统
A：文件系统就是帮助管理存储空间的系统，当前实验所使用的是类 Unix 系统，通过建立引导块、超级块等组件帮助管理存储空间。

Q：现在我需要创建proc文件夹/目录，应该是通过什么方式？该方式是否会向 存储计算机上文件信息的地方（硬盘存储了，但是想要显示应该离不开 挂载） 存储有关自己的信息？
A：方式参照 实现。会，因为是通过 mkdir 、mknod 实现的。

Q：什么是挂载？做了哪些事？
A：我认为就是读取一个存储硬件上的文件系统中的描述信息，识别这个存储硬件的使用情况。AI：在 Linux、Unix 等类 Unix 操作系统中，挂载（Mount） 是将外部存储设备（如硬盘分区、U 盘、光盘、网络存储等）或虚拟文件系统与系统根文件系统（/）下的某个目录建立关联的过程。挂载的本质是 **“给存储设备分配系统可识别的访问入口”**，核心是通过内核建立 “硬件设备 - 文件系统 - 挂载点” 的关联，让操作系统能将 “树形目录访问” 转化为 “硬件数据块读写”，最终实现对设备内容的透明访问。

Q：什么是软盘？
A：软盘是计算机 “早期移动存储” 的代表，总而言之就是早期移动存储设备。

Q：读一个文件的流程是怎么样的？open和read似乎是分开的流程。
A：cat的功能是将文件的内容打印到标准输出，核心实现大致就是先open，再read。open的作用**建立并返回**文件的描述符fd，然后read就可以根据fd读文件了。之所以有这个问题是因为通过第一张图片可以得到 打开文件没有问题，sys_read出了问题 的结论（实验提示），根据sys_read的内容就可以知道这个结论的正确性，因为对应的输出内容（(Read)inode->i_mode=...）就是在sys_read当中输出的。

Q：fd对于一个文件来说的作用是什么？fd是在什么时候确定的？是open的时候才有的，还是创建文件的时候就会有？
A：似乎是可以起到一个定位文件的作用，因为read就是通过该参数就找到了文件，并将文件的内容复制到了buf再输出。在 fs\open.c 中的 sys_open 可以看到，fd是打开这个文件时获得的，相当与就是有一个表会记录打开的文件，open会在这个表中找到空闲的位置去放该打开的文件，fd就是该文件在这个表中索引。

Q：程序中申请内存是由谁完成的？需要通过操作系统吗？因为申请内存就需要知道内存的使用情况，而内存的使用情况是由操作系统管理的，如果这样的话编译器就会依赖于操作系统，换言之就是不同操作系统有不同的编译器安装包（不确定）。不然的话就是各个操作系统有统一的规定将内存的情况存放在哪里。如果编译器依赖于操作系统的话，那么开发一个新的操作系统不就也需要开发一个新的编译器了吗？这样不够模块化。
A：gcc的源码安装包就是一样的，估计不管是什么操作系统有了相应的工具都是可以安装的。编译器的作用就是将高级语言转化为机器码，而机器码只要在相同硬件的基础上应该都是一样的，所以编译器在不同操作系统应该不会有什么两样。感觉不同的操作系统应该都会提供相同的 接口 ，似乎只有这样编译器才能拥有自己的库（不依赖操作系统）。所以申请内存应该也是这个道理吧。所以估计重点就是“接口”、“协议”。

#### 需求
自动创建 /proc、/proc/psinfo、/proc/hdinfo、/proc/inodeinfo，中间两者内容可读
#### 实现
##### 思路
Linux 0.11 使用的是 Minix 的文件系统，这是一个典型的基于 inode 的文件系统。它的每个文件都要对应至少一个 inode，而 inode 中记录着文件的各种属性，包括文件类型。文件类型有普通文件、目录、字符设备文件和块设备文件等。在内核中，每种类型的文件都有不同的处理函数与之对应。我们可以增加一种新的文件类型——proc 文件，并在相应的处理函数内实现 procfs 要实现的功能。（Linux 0.11 还没有实现虚拟文件系统，也就是，还没有提供增加新文件系统支持的接口。所以本实验只能在现有文件系统的基础上，通过打补丁的方式模拟一个 procfs。）
##### 步骤
1、添加新文件类型。在 include/sys/stat.h 中添加相应的宏定义与宏测试。
2、让mknod支持新的文件类型。修改 fs\namei.c 中的 sys_mknod 部分。
3、procfs初始化（创建目录和结点）。由于这个步骤得执行在挂载根目录（在 init() 中实现）之后，所以是执行在用户态（init执行在用户态），而mkdir和mknod是系统调用，所以需要添加接口去调用。
4、让proc文件可读。首先在 fs\read_write.c 中的sys_read当中的if排比句中添加proc类型文件的判断，并调用proc_file_read函数处理（记得在该文件中声明处理函数为外部函数）。然后在 fs\proc.c 文件中实现proc类型文件处理函数。

#### 理解
![cat的核心实现](image-2.png) cat、read也是一个面向对象的编程，read会读取对应文件的内容到cat提供的一个buf中，cat的buf有多大，read就会最多读出那么大的内容。那么为了能够将文件的内容读完，cat就需要循环调用read，而read会记录上次读完后的位置，所以再次读的时候就可以接着读。当全部内容读完的时候，read（也可以说是对应的处理函数）就会返回0，表示没有内容可以读了，至此文件所有内容均读完了，循环也结束了，只有在最后加上\0就可以打印到标准输出中了（估计涉及到了打印到标准输出的原理，猜测就是一个循环，直到读到\0结束）。
